## Наблюдения

- **Общая модель доступа.** Профиль, публичный список и карточка используют общее серверное чтение и `VisibilityPolicy`. Различающиеся проверки допустимости сегмента на входе страницы и API оставляют риск расхождения для некорректного ввода. Пограничное поведение API требует проверки. [Чтение](../../apps/web/src/actions/wishlist-read.ts) · [Страница](../../apps/web/src/app/l/%5Btoken%5D/link-page.ts) · [API](../../apps/web/src/actions/public-wishlist.ts)
- **HTTP-проверки публичного адреса.** Из-за проверки доступа до редиректа браузер получает 404 и для скрытой карточки. Тест CI поднимает сервер и проверяет невалидный токен списка и приглашения. Для карточки и блокировки пользователя с сессией есть тесты с моками и свидетельства со staging. Регрессия итогового HTTP-статуса карточки может пройти CI. [HTTP-проверка CI](../../apps/web/scripts/verify-public-404-http.mjs#L40) · [Тесты страницы](../../apps/web/src/app/l/%5Btoken%5D/%5BgiftId%5D/page.test.tsx) · [Отчёт приёмки](epic-3-qa-report.md)
- **Канонизация адреса API.** Запрос к `/api/v1/l/` без токена на staging получил 308 на канонический адрес `/api/v1/l`. Спека реализации 3.3.1 описывает 404 для отсутствующего токена и отдельно упоминает адрес с завершающим слешем. Критерий 404 для публичных страниц с токеном прошёл. [Спека 3.3.1](spec-3-3-1-public-token.md) · [Маршрут API](../../apps/web/src/app/api/v1/l/%5B%5B...token%5D%5D/route.ts)
- **Обновление профиля после действия.** PR #126 закрепил перезапрос после подписки и принятия заявки. Удаление из друзей сразу скрывает личные данные и восстанавливает их при ошибке. Тесты ошибки проверяют откат дружбы и списка желаний. Фикстуры в этих тестах не заполняют «Обо мне», поэтому восстановление поля остаётся без отдельного утверждения. [Обработчик](../../apps/mobile/app/%28app%29/u/%5Bnick%5D.tsx#L610) · [Тесты](../../apps/mobile/src/session/profile-screen.test.tsx#L1273) · [PR #126](https://github.com/Clever-Agency/Gift-list/pull/126)
- **Смена зрителя при открытом списке.** Экран веб-приложения привязывает результат к токену. Если экран остаётся смонтированным и сессия сменяется без промежуточной загрузки, данные предыдущего зрителя могут остаться на экране. Достижимость такого перехода через штатную навигацию требует проверки. [Экран](../../apps/mobile/app/%28link%29/wishlist/%5Btoken%5D.tsx#L90)
- **Поиск и ограничения выборки.** PostgreSQL ограничивает две выборки до точной фильтрации и ранжирования в приложении. На насыщенной выборке SQL-шаблон и буквальное сравнение могут отобрать разные строки. Моки используют буквальное сравнение, поэтому этот риск требует проверки на PostgreSQL. Для ранее созданных аккаунтов стоит в том же прогоне проверить нормализацию имён при миграции. Staging-прогон использовал новые аккаунты. [Поиск](../../apps/web/src/actions/search-users.ts#L81) · [Тест](../../apps/web/src/actions/search-users.test.ts#L64) · [Миграция](../../apps/web/src/db/migrations/20261112120000_user_search_name_normalized/migration.sql#L13)

## Проверка поведения

На staging подтверждены смена ника с сохранением токена списка, поиск и его отключение, матрица видимости, открытие списка и карточки из браузера, а также HTTP 404 для недоступных ссылок. После подписки и принятия заявки профиль обновился без перезагрузки. На том же URL перевод публичного желания в скрытое дал HTTP 404. Прошли 507 целевых тестов и CI staging. В отчёте приёмки перечислены границы ручного прогона. [Отчёт приёмки](epic-3-qa-report.md)

Во время ретроспективы повторно проверены два отсутствующих адреса staging, список и карточка желания. Оба вернули HTTP 404 без `Location` и с `noindex`.

## Последующие действия

Предлагаемые владельцы указаны по области кода.

1. **Веб и QA.** Добавить проверку HTTP 404 и отсутствия редиректа для недоступной карточки, включая сессию и Block. Проверить единый ответ страницы и API для некорректного сегмента и согласовать контракт для завершающего слеша. Повторить полный переход с карточки через вход до подтверждения брони в браузере.
2. **Сервер.** Проверить поиск по нику, содержащему подчёркивание, на заполненной тестовой базе и сравнить нормализацию миграции старых аккаунтов с `normalizeForSearch()`. Покрыть расхождения регрессионными тестами.
3. **Клиент.** Проверить смену зрителя при открытом вишлисте. Добавить в тест отката удаления друга проверку, что «Обо мне» сначала скрывается и восстанавливается при ошибке.

`accepted-with-open-items`. Все пять историй завершены, заявленные сценарии из отчёта приёмки подтверждены на staging и автоматикой.
