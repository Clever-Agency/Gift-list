# Epic 4 Context: Дружба, подписка, приглашение

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Эпик задаёт круг доступа к вишлисту: взаимную дружбу, подписку, приглашение по ссылке, удаление из друзей и блок. После принятого приглашения обе стороны видят желания «друзьям» друг друга, подписка даёт только «всем», а разрыв отношений или блок сразу снимает видимость — без раскрытия скрытого, без счётчика спрятанных желаний и без снятия чужих броней. Экраны — в приложении (Android, iOS, браузер); у приглашения по ссылке есть ещё серверная страница Next.js для превью и перехода.

## Stories

- Story 4.1: Отправка Приглашения в друзья
- Story 4.2: Принятие и отклонение Приглашения
- Story 4.3: Друзья, подписки и заявки
- Story 4.4: Удаление из друзей
- Story 4.5: Блокировка и разблокировка
- Story 4.6: Подписка
- Story 4.7: Ссылка-приглашение `/i/:token`

## Requirements & Constraints

- **Дружба взаимна и только по принятому приглашению.** Пока приглашение pending, «друзьям» не видит никто. Повтор при pending не создаёт дубликат, при уже существующей дружбе — no-op с пояснением, через блок — `FORBIDDEN`; встречное pending сразу даёт дружбу.
- **Принятие** — одна транзакция: ребро пары и удаление всех приглашений между ними. **Отклонение и отмена** удаляют приглашение и включают кулдаун 24 ч на новое приглашение той пары; отправитель видит «отклонено».
- **Экран «Друзья»**: вкладки «Друзья», «Подписки», «Запросы» с badge входящих; входящие выше исходящих; исходящая — «Ожидает ответа» + «Отменить». Поиск среди друзей по имени и @нику без учёта регистра (`@` необязателен), счётчик «N из M»; подгрузка по курсору порциями по 15, поиск по всему списку, а не по загруженной части. «Подписки» — те, на кого подписан; подписчики — отдельным переключателем с «Убрать подписчика».
- **Удаление из друзей** доступно любой стороне: ребро и приглашения пары удаляются, «друзьям» сразу не отдаются ни в профиле, ни по `/l/:token` (там только «всем», без числа скрытых). Новая дружба — только через новое принятое приглашение. Активная бронь бывшего друга сохраняется и видна ему только как reservation card.
- **Блок** рвёт дружбу, отменяет pending и удаляет подписки в обе стороны; профиль и `/l/:token` дают `not_found` в обе стороны; новые приглашения и подписки запрещены; чужую бронь блок не снимает. Разблокировка дружбу и подписку не восстанавливает.
- **Подписка** — без подтверждения, только «всем» (без «друзьям», ДР и личных дат); отписаться может подписчик, убрать подписчика — цель; повтор — no-op.
- **Ссылка-приглашение** одна на пользователя и неизменна. Регистрация по `/i/:token` в той же транзакции создаёт дружбу, если нет блока; вошедший подтверждает явно; превью мессенджером ничего не создаёт. Регистрация по `/l/:token` дружбу не создаёт никогда.
- **Приватность.** Скрытые желания не объясняются и не считаются; блок неотличим от несуществующего профиля или ссылки.

## Technical Decisions

- **AD-10.** Друг — строка `Friendship`, а не статус приглашения; pending — направленный `FriendshipInvite`. Принятие в одной транзакции вставляет `Friendship(userLowId, userHighId)` с UNIQUE по паре и удаляет **все** приглашения пары; встречное pending принимается тем же протоколом. Reject/cancel пишет `InviteCooldown(pair, until = now + 24 ч)`. Unfriend удаляет дружбу и приглашения пары; Block дополнительно удаляет `Subscription` в обе стороны и вставляет `Block`. Подписка не проходит фильтр «друзьям».
- **AD-19.** `Subscription(subscriberId, targetId)` уникальна, создаётся без подтверждения, даёт только `PUBLIC`; снятие — любой стороной.
- **AD-21.** Один immutable invite-token, путь `/i/:token`; регистрация с токеном создаёт `Friendship` в той же транзакции при отсутствии `Block`; `/l/:publicToken` не создаёт ни дружбу, ни подписку.
- **AD-7.** `Friendship` открывает `FRIENDS`; `Block` в любую сторону переводит список и профиль в `not_found` (шаг 2 политики); после unfriend/block держатель брони видит только reservation card. Рёбра меняет только доменный слой, не запросы из экранов.
- **AD-1 / AD-17.** Мутации — доменный модуль `domain/friendship`, его вызывают Server Actions, `app/api/v1` и страница `/i`; правила не дублируются. Приложение ходит только в `api/v1`; `/i/:token` — серверная страница Next.js.
- **AD-12.** `{ ok: true, data } | { ok: false, code, message, reason?, field? }`, закрытые коды (`FORBIDDEN`, `CONFLICT`, `VALIDATION`, `NOT_FOUND`, `RATE_LIMITED`); `reason` — zod-enum, текст — по ключу перевода. Типы списков людей и заявок — в `packages/contracts`.
- **AD-13 / AD-27.** Сравнение имён и ников — только `normalizeForSearch()` (NFC, нижний регистр, `ё → е`); строки — из каталогов переводов, имя продукта — переменная бренда, литералов в компонентах нет.
- **AD-15 — обязательные тесты.** Block с валидным токеном → `not_found`; unfriend при активной брони → reservation card без остальных желаний; подписчик не получает `FRIENDS` и даты; регистрация по `/l/` не создаёт дружбу, по `/i/` создаёт.

## UX & Interaction Patterns

- **Сегмент «Друзья · Подписки · Запросы»** — настоящие вкладки (`tablist`/`tab`/`tabpanel`, стрелки, `selected`, выбранное состояние не только цветом); badge входит в подпись («Друзья, 2 запроса»). «Запросы»: «Принять» (primary) / «Отклонить» (ghost) у входящих, «Отменить» у исходящих. «Подписки» — переключатель «Я подписан (N) · Мои подписчики (N)», выбор запоминается.
- **Строка человека и ⋯ — одно правило** для поиска, друзей, подписок, подписчиков и профиля (в профиле — кнопками). Чип показывает одно, самое сильное отношение; у друга пунктов подписки нет; при встречном приглашении «Добавить в друзья» — это «Принять приглашение»; в кулдауне кнопка недоступна с подписью «Можно снова через N ч».
- **Действия.** Подтверждение только для «Удалить из друзей», «Убрать подписчика» и «Заблокировать»; остальное — сразу с toast. После действия строка остаётся, меняется только чип, фокус возвращается на ⋯; из «Подписок» и «Моих подписчиков» строка исчезает. Optimistic UI с откатом и toast «Нет сети. Попробуйте ещё раз.».
- **Блок** — в ⋯ профиля и любой строки; confirm объясняет взаимную невидимость и что чужая бронь останется. Разблокировка — Настройки → «Заблокированные».
- **Пустые состояния** для каждой вкладки и поиска по друзьям заданы в UX-спеке; нулевой поиск говорит «Никого не нашли по «{запрос}»», а не «скрыто».
- **`/i/{token}`.** Анониму — «{имя} приглашает вас в друзья» и что даёт дружба; «Принять приглашение» ведёт в регистрацию с токеном (браузерная сборка или App Link). Вошедшему — «Добавить {имя} в друзья?». Своя ссылка, уже друзья, невалидный токен и блок дают каждый свой один текст; копирование ссылки-приглашения есть в «Моём вишлисте» и в пустом состоянии «Найти знакомых».

## Cross-Story Dependencies

- 4.1 задаёт модель рёбер и DTO; 4.2–4.6 используют её: новое действие — метод домена, а не свой запрос из экрана.
- 4.3 читает дружбу, pending, подписки и подписчиков, поэтому опирается на 4.1, 4.2 и 4.6.
- 4.4 и 4.5 не трогают поля брони: reservation card после потери доступа — Epic 5 (Story 5.5), контракт принимается как есть.
- Точки входа «Добавить в друзья» / «Подписаться» и статусы отношений на профиле и в поиске — Epic 3.
- Уведомления `FRIEND_INVITE`, `FRIEND_ACCEPT`, `FRIEND_REJECT` и доставка — Epic 6; здесь только события и данные.
- Экран «Заблокированные» — настройки Epic 6; Story 4.5 даёт действие домена, доступное оттуда.
- `/i/:token` делит с `/l/:token` серверный рендер, мета-теги и выбор языка (AD-26, AD-27); регистрация с токеном — поток Epic 1, который должен пронести токен до создания аккаунта.
- Сверка телефонной книги (Epic 8) даёт доступ к «всем» через `ContactMatch`, но подписку не создаёт: «Подписаться» — отдельное действие этого эпика.
