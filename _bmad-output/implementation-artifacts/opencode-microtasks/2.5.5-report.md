## Что сделано

### Контракт (`packages/contracts/src/gift.ts`, `index.ts`)

- `giftTagInputSchema` — strict-union: `{ catalogId: string }` для фиксированного тега или `{ text: string }` для своего. Ровно один источник; оба или ни одного — `VALIDATION`.
- `GIFT_TAG_TEXT_MAX = 30`. Свой текст: `trim()`, непустой, длина — по кодовым точкам Unicode (`[...value].length`). Это совпадает с `VARCHAR(30)` PostgreSQL, который считает символы, а не UTF-16 единицы: эмодзи вне BMP — один символ в БД и два JS-юнита.
- `U+0000` отклоняется: PostgreSQL не хранит NUL в `text`/`varchar`, иначе тело проходило бы контракт и падало 500 вместо `VALIDATION`.
- Список тегов отклоняет дубли: одинаковый `catalogId` или одинаковый текст после `trim()`. Сравнение точное (с учётом регистра), как байтовые uniques `(giftId, tagId)` и `(giftId, customText)`; нормализация сверх trim не выдумывалась.
- `giftInputSchema.tags` необязателен и по умолчанию `[]`; `giftUpdateSchema.tags` необязателен и попадает в `GiftUpdate`, только если пришёл, — поэтому PATCH без ключа сохраняет теги.
- `aggregateEligible`, `tagId` и прочие поля модерации strict-схемой отклоняются: клиент не может задать допуск в агрегаты.

### Домен (`apps/web/src/domain/tag.ts`)

- `toGiftTag`/`toGiftTags`: фиксированный тег → `{ catalogId, label }`, где `label` выбирается `pickTagLabel(labels, locale)` на сервере; свой → `{ catalogId: null, label: customText }` без перевода (AD-27).
- Одобренный ADMIN тег с `tagId` и `customText` показывает каталожную подпись: одобрение нормализовало текст в каталог.
- Строка без пригодной подписи отбрасывается, как в каталоге 2.5.4; `slug` как подпись не подставляется — AD-27 требует `label`.
- `toOwnerGiftCard` и `toViewerGiftCard` принимают локаль (по умолчанию `DEFAULT_LOCALE`) и маппят теги; на провод уходят только `catalogId` и `label`.

### Use-case (`apps/web/src/actions/gifts.ts`)

- `createGift`: проверка существования всех фиксированных id через `Tag.findMany`, затем вложенный `tags.create` в том же `gift.create` — атомарно с желанием. Фиксированный тег пишется с `aggregateEligible: true`, свой — `false`.
- `updateGift`: если `tags` пришёл — `$transaction`: проверка id → `gift.update` с владельцем/архивом/`OPEN`-гейтом → `giftTag.deleteMany` → `giftTag.createMany` → повторное чтение карточки. Ошибка на любом шаге откатывает всё; чужое или архивное желание падает до записи тегов.
- `tags` отсутствует — прежний путь одним `gift.update` без транзакции и без чтения тегов.
- `tags: []` очищает набор: в UI-спеке у своего тега есть «Убрать тег», значит удаление поддерживается (DESIGN.md, Tag picker).
- Теги не получили собственного статусного ограничения: AD-8 разрешает править поля `RESERVED`; `OPEN`-гейт остаётся только у `visibility` (Story 2.3) и `quantity` (Story 2.5). `CLOSED` ведёт себя как остальные не-`OPEN` поля — отдельного правила в AC нет, новое ограничение не выдумывалось.

### Чтение (`wishlist-read.ts`, `my-gifts.ts`)

- `readWishlist` принимает `locale` и добавляет в выборку только `tagId`, `customText`, `tag.labels`; `getMyGifts` берёт локаль из `Accept-Language` через `negotiateLocale(preferredFromAcceptLanguage(...))`, как каталог и регистрация.
- `VisibilityPolicy` не менялась: скрытые желания по-прежнему отсекаются до маппинга, теги скрытого желания в ответ не попадают.

## Решения с источниками

1. **Форма входа — `catalogId` / `text`, а не `id`.** DTO карточки уже использует `catalogId` (`packages/contracts/src/index.ts`), а `tag.ts` фиксирует, что `id` каталога хранится на желании как `catalogId` (AD-12).
2. **Длина — кодовые точки.** `VARCHAR(30)` в PostgreSQL считает символы; `z.string().max(30)` считал бы UTF-16 единицы и отклонял бы текст, который БД принимает. Правило зафиксировано в контракте и тесте на 30/31 эмодзи.
3. **Дубли — точное совпадение после trim.** Схема 2.5.3 объявляет уники `(giftId, tagId)` и `(giftId, customText)`; F-2.5.3-4 требует только trim в write-path. Регистронезависимая нормализация — Story 10.2, здесь не изобреталась.
4. **PATCH без `tags` сохраняет, `tags: []` очищает.** PATCH — частичное обновление; пустой массив — явная замена на пустой набор, а UI-спека прямо предусматривает удаление своего тега.
5. **Флаг агрегатов ставит только сервер.** AD-22: фиксированные теги в агрегатах, свои — после одобрения. F-2.5.3-3/-4 закрыты этим writer-ом.
6. **Язык подписи — `Accept-Language`, fallback `DEFAULT_LOCALE`.** AD-27: сервер кладёт `label` на языке запроса; клиент подписей не держит.
7. **Ответ карточки — только `catalogId` и `label`.** AD-12/AD-22: модерация и агрегатный флаг не уходят клиенту; strict-схема `giftCardSchema` это проверяет.
8. **Статусные ограничения — только документированные.** Story 2.3/2.5 закрепляют `OPEN` для `visibility`/`quantity`; AD-8 разрешает правку полей `RESERVED`; для тегов отдельного правила нет.
9. **Порядок тегов — стабильный порядок БД (`createdAt`, `id`), не порядок показа.** Ручного `sortOrder` в схеме нет; до трёх чипов и «+N» — решение карточки Story 2.5.7. Комментарий в select это фиксирует.

## Находки: предлагаемые fixup-микротаски (не реализованы)

### Настоящие дефекты / требуют решения

1. **F-2.5.5-1: порядок тегов не задан.** Порядок строк — `createdAt`, `id`; у `createMany` `createdAt` одинаков, поэтому порядок между тегами одного набора случаен. Нужен `sortOrder`/позиция или явное правило сортировки для карточки Story 2.5.7 (и тест на реальной БД).
2. **F-2.5.5-2: нет лимита числа тегов.** Контракт не ограничивает длину массива; тело до 32 КБ может создать сотни строк на одно желание. Продуктового лимита в AC/UX нет («Несколько можно»), поэтому решение — за Story 2.5.6 (picker) вместе с текстом ошибки.
3. **F-2.5.5-3: теги у `CLOSED`.** AC молчит; сейчас теги правятся у закрытого желания так же, как название. Нужно продуктовое решение до Story 2.6/2.5.7: разрешать, запрещать или скрывать редактор.
4. **F-2.5.5-4: фиксированный тег без подписи теряется на карточке.** Если ADMIN создаст `Tag` без `ru`-подписи, строка отбрасывается (как в каталоге). Story 10.2 обязана требовать подпись для каждого `SUPPORTED_LOCALES`; иначе возможен fallback-контракт.
5. **F-2.5.5-5: гонки каталога не отображены в конверт.** В create проверка id идёт до вложенной записи: удаление тега ADMIN между ними даст необработанный P2003; уникальная гонка в update может дать P2002. Нужно отобразить P2003/P2002 в `VALIDATION`/`CONFLICT` или закрыть каталог от удаления при связях (Story 10.2).
6. **F-2.5.5-6: нет интеграционной проверки на PostgreSQL.** Вложенный create, `$transaction`, `createMany`, CHECK-ограничения и реальный откат проверены только моками. Нужна одноразовая локальная/CI-БД (продолжение F-2.5.4-3).

### Запланированная работа (не дефект этого среза)

7. **F-2.5.5-7: поле ошибки элемента `tags.N`.** Ошибка отдельного тега приходит как `tags.0.text` и на клиенте показывается общим сообщением; picker 2.5.6 должен отобразить её у поля «Свой тег» (или контракт — отдавать `tags`).
8. **F-2.5.5-8: контракт для picker.** `giftTagListSchema` не экспортирован, у `catalogId` нет max; 2.5.6 может импортировать правило или экспортировать список. Не требуется этим срезом.
9. **F-2.5.5-9: повторная отправка того же набора перезаписывает строки.** `deleteMany`+`createMany` меняет `GiftTag.id`/`createdAt` и бумпает `Gift.updatedAt`; можно сравнить с сохранённым набором и не писать. Оптимизация, не дефект.
10. **F-2.5.5-10: дублирование select и negotiate.** Блок `tags` есть в `gifts.ts` и `wishlist-read.ts`, локаль — в `gifts.ts` и `my-gifts.ts`; общий helper уменьшит риск рассинхрона.
11. **F-2.5.5-11: `F-2.5.3-3`/`F-2.5.3-4` закрыты.** Фиксированные теги пишутся с `aggregateEligible=true`, свой текст тримится и проверяется по длине; отдельная работа не нужна, запись для истории.
12. **F-2.5.5-12: сид и деплой (F-2.5.3-1/F-2.5.4-2).** Не входит в срез; после выката `Tag` останется пустой без `db seed`, и теги нельзя будет выбрать, пока каталог не засеян.
