## Что сделано

`GET /api/v1/l/:token` — публичное чтение чужого списка по ссылке. Это тонкий адаптер AD-12 над единственным чтением `readWishlist({ viewer, target: { publicToken }, viaListToken: true, locale })` (AD-7):

- зритель — сессия приложения через `auth.api.getSession({ headers })`, иначе `null`; поддельная или просроченная cookie просто даёт анонимный ответ;
- язык — `negotiateLocale(preferredFromAcceptLanguage(Accept-Language))`, иначе `ru` (AD-27);
- видимость не пересчитывается: аноним получает только `PUBLIC`, друг — `PUBLIC` и `FRIENDS`, `SECRET` — только владелец, архив не читается; `Block` и неизвестный токен дают один и тот же `{ access: "not_found", gifts: [] }` до чтения желаний;
- токен принимается только как один безопасный сегмент: пустой, длиннее 128 символов, с `/`, `\`, `%2f`, `%5c` или из нескольких сегментов получает `not_found` без обращения к БД и без записи токена в лог; для этого маршрут сделан optional catch-all `/l/[[...token]]`, иначе такие запросы уходили бы в общий 404 `api/v1/[...slug]` с другим статусом;
- ответ `toResponse` несёт `Cache-Control: private, no-store`, у неподдерживаемых методов — тот же `NOT_FOUND` в конверте AD-12; `HEAD` не переопределён, Next выводит его из `GET`, как в соседнем `/api/v1/me/gifts`.

Ответ списка при `access: "gifts"` теперь дополнительно содержит владельца `{ displayName, nick }` из `User.name` и `User.nick` — только при чтении по ссылке, чтобы странице `/l` и экрану приложения было чем заполнить заголовок. В `readWishlist` владелец читается одним `select` relation-поля `owner: { select: { name, nick } }`, поэтому своего запроса на `User` нет, а `publicToken` по-прежнему получает только владелец. Пустой список (`allowed.length === 0`) тоже называет владельца. Чтение `/me` (`getMyGifts`) форму ответа не меняет: блок `owner` в нём не появляется.

Флаг `viaListToken` учитывается только при `target: { publicToken }`: чтение по `ownerId` не может открыть `PUBLIC` из-за случайно переданного флага (страховка для `/u/:nick` из 3.4).

Контракт: в `packages/contracts` добавлен `strictObject` `listOwnerSchema { displayName, nick }`, в `listDataSchema` — необязательное поле `owner` только у ветки `gifts`; `not_found` остаётся без него, лишние поля отвергаются.

## Ревью

Разбор находок — в `## Review Triage Log` спеки (проход 3.3.1); в этой сессии ревью не перезапускалось. Уже исправлено: `viaListToken` больше не действует вне token-target (high), лишний `HEAD` убран (low), тест на пустой ответ по ссылке проверяет владельца (medium), друг проверяется на отсутствие `publicToken` (low), уточнён комментарий контракта.
