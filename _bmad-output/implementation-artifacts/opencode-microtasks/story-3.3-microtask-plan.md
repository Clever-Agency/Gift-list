## Что уже есть и чего нет

Есть и переиспользовать:

- `readWishlist` (`apps/web/src/actions/wishlist-read.ts`) — единственное чтение списка. Аноним с `viaListToken: true` получает только `PUBLIC` (`VisibilityPolicy.allowedVisibilities`). Друг с тем же флагом получает `PUBLIC` и `FRIENDS`. `Block` и неизвестный токен оба дают `{ access: "not_found", gifts: [] }` до чтения желаний. `publicToken` в ответе только владельцу.
- `toViewerGiftCard` — карточка зрителя без `ownerAction`.
- `packages/ui`: `WishCard`, `EmptyState`.
- `NEXT_OWNED_PREFIXES` уже включает `/l`. SPA fallback на `/l` и `/l/*` не претендует (`apps/web/src/lib/spa-paths.ts`).
- App Links уже объявляют `/l/*` и `/wishlist/*`. `.well-known` не трогать.
- `safeNextPath` принимает только относительный путь. `/l/tok_1` переписывается в `/wishlist/tok_1`. Абсолютные URL и `//` становятся `/`.
- Заглушка `apps/mobile/app/wishlist/[token].tsx`: анонима уводит на `/login` с `next=/wishlist/${token}`. Списка желаний там нет.
- Вход и регистрация не создают дружбу от `/l` (AD-21). Это не менять.

Нет:

- страницы `apps/web/src/app/l/[token]`;
- `GET` в `api/v1` для чужого списка по токену;
- имени и ника владельца в `listDataSchema` (сейчас только `access`, `gifts`, опциональный `publicToken`).

## 3.3.1 — чтение по токену

Намерение для `bmad-build`: добавить публичное чтение списка по `publicToken` для `GET /api/v1/l/:token`. Внутри только `readWishlist({ viewer, target: { publicToken }, viaListToken: true, locale })`. Аноним: `viewer: null`. Сессия приложения: viewer из `getSession`. Локаль из `Accept-Language` через `negotiateLocale`.

Когда `access` равен `gifts`, ответ дополнительно содержит владельца `{ displayName, nick }` из `User.name` и `User.nick`. На `not_found` этих полей нет и желаний нет. `publicToken` по-прежнему не отдавать зрителю, который не владелец. Скрытые желания не читать: существующий `where` по `allowedVisibilities` не ослаблять.

Токен — один сегмент пути. Пустой, с `/`, `\`, `%2f`, `%5c` или длиннее разумного идентификатора не искать в БД отдельным сообщением: тот же `not_found`, что и у неизвестного токена. Не логировать токен.

Тесты `apps/web`: аноним видит только PUBLIC; друг — PUBLIC и FRIENDS; подписчик без флага ссылки не видит чужой PUBLIC только из-за этого маршрута, если флаг забыт — тест как раз требует флаг; Block и неизвестный токен сравниваются побайтно по безопасному телу (нет title скрытых); владелец своей ссылки видит и SECRET, потому что политика владельца уже так устроена, и получает `publicToken`. Заголовок ответа `Cache-Control: private, no-store`.

Не делать: страницу `/l`, экран Expo, бронь, дружбу, миграцию.

## 3.3.2 — страница Next `/l/[token]`

Намерение: серверная страница `apps/web/src/app/l/[token]/page.tsx`. Перед рендером `auth.api.getSession`. Сессия есть — `redirect` на `/wishlist/` плюс этот же сегмент после проверки, что это один безопасный сегмент (без схемы, без `//`, без `..`). Цель не брать из query, `Referer`, cookie и не прогонять сырой pathname через `safeNextPath`: `/l/abc/../../admin` сейчас схлопывается в `/admin` (`packages/contracts/src/auth.test.ts`). Поддельная cookie, которую `getSession` не признаёт, остаётся анонимной страницей, а не редиректом.

Аноним: `readWishlist` как в 3.3.1 с `viewer: null`. Имя — `h1` (`display-sm` по DESIGN), под ним `@nick`. Карточки — `WishCard` из `@gift-list/ui`, без чипа видимости и без счётчика скрытых. Пустой `gifts` при `access: "gifts"` — EmptyState «Пока нет открытых желаний». `not_found` — одна страница «Список не найден» и `title` «Список не найден — {brand}». Это текст DESIGN для исхода эпика «не найдено». Отдельной фразы для Block нет.

«Куплю сам» — `<a>` только если `quantity === "SINGLE"` и `status === "OPEN"`. Видимый текст «Куплю сам», `aria-label` «Куплю сам: {название}». `href` — `/wishlist/{token}` того же сегмента. Экран подтверждения брони не строить. Регистрация с этой ссылки дружбу не создаёт; новый код дружбы не добавлять.

`generateMetadata` вызывает тот же отфильтрованный результат, не отдельный запрос всех желаний. В метаданных только имя владельца и бренд, либо not-found. Нет названий, цен, описаний, фото, числа скрытых.

Язык страницы: `negotiateLocale` от `Accept-Language`, иначе `ru`. `lang` у `<html>` этой страницы — выбранный язык. Корневой `layout.tsx` сейчас всегда `lang="ru"`; админка должна остаться `ru` (AD-27). Не переключать язык всех маршрутов. Ответ: `Cache-Control: private, no-store` и `Vary: Accept-Language`.

Тесты: HTML анонима содержит PUBLIC title и имя, не содержит SECRET/FRIENDS title; метаданные не содержат эти title; Block и мусорный токен дают один и тот же текст и статус; сессия даёт редирект ровно на `/wishlist/{token}`; cookie-мусор не даёт `Location` на чужой хост; `UNLIMITED` без ссылки «Куплю сам».

Не делать: экран списка в Expo (следующая микрозадача), `.well-known`, Epic 5.

## 3.3.3 — экран приложения `/wishlist/[token]`

Намерение: заменить заглушку `apps/mobile/app/wishlist/[token].tsx`. Анонима по-прежнему отправлять на `/login` с `next`, который `safeNextPath` оставляет путём `/wishlist/{token}` и ничем иным. Вошедший запрашивает `GET /api/v1/l/:token` через существующий `apiRequest` (cookie на вебе, bearer на телефоне). Рисовать имя, `@nick` и карточки из `packages/ui`. Пусто и «не найдено» — те же фразы, что на странице Next, ключи каталога `app` или общие, без второй формулировки. Друг видит FRIENDS, потому что сервер уже применил политику; клиент видимость не пересчитывает.

Тесты экрана: мок API; PUBLIC и FRIENDS рисуются; скрытый title из фикстуры, которого нет в ответе, не появляется; пустой список и `not_found`; аноним не вызывает API и уходит на логин с безопасным `next`.

Затем полный `npm test` и `npm run build`. Историю не переводить в `done`.

## Не решать заново

Обычные уже записанные правила, отдельное одобрение не нужно:

- один список, URL только `/l/:publicToken`, без `?listId` (AD-6);
- чтение только через `VisibilityPolicy` (AD-7, CLE-48);
- регистрация с `/l` не создаёт дружбу (AD-21);
- один домен, `/wishlist` отдаёт SPA, не Next (AD-26);
- язык страницы из `Accept-Language`, без локали в пути (AD-27);
- тексты из каталога, бренд аргументом `{brand}`;
- бронь и confirm — Epic 5, в эту историю не входят;
- фото на `/l` — только у желаний «всем», когда фото появятся (Story 2.7). Сейчас фото в карточке нет, мета их не добавляет.

## Где спецификация расходится, и как не выдумать правило

- Эпик говорит «не найдено», DESIGN — «Список не найден» и заголовок «Список не найден — {BRAND}». Это одна ситуация. В UI берётся строка DESIGN. Второе сообщение для Block не добавлять.
- AD-7 в «Prevents» упоминает «404 как маскировка Block», а в правиле Block и неизвестный токен оба `not_found`. Следовать правилу: ответы неотличимы. Какой именно HTTP-статус у этой пары, эпик не задаёт; у обоих он один и тот же.
- DESIGN для «Куплю сам» говорит ещё и про открытый confirm желания. Пользователь этой задачи и Linear выносят саму бронь в Epic 5. Ссылка ведёт на `/wishlist/{token}`. Имя query для confirm не придумывать.

Открытых продуктовых решений, без которых нельзя писать 3.3.1–3.3.3, нет.
