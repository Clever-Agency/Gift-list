## Intent

Добавить `npm run test:affected` и сравнить длительность и число тестовых файлов с `npm test` на нескольких типичных PR, влитых в `staging`. Сохранить обязательный полный прогон в CI.

</frozen-after-approval>

## Implementation Notes

Без истории продукта. Переиспользуем `scripts/run-suite.mjs` и постоянный набор `node:test`. Для изменений внутри приложений Vitest выбирает тесты по графу импортов. Проверки, читающие исходники с диска, явно входят в выборку соответствующего приложения. Для общих пакетов, конфигурации, миграций, удалений и неопределённой базы запускается полный набор.

- `npm run test:affected` сравнивает текущую рабочую папку с общей базой `HEAD` и `origin/staging`, включая новые файлы.
- `npm run test:affected -- --base <ref>` берёт изменения из коммитов между общей базой и `HEAD`, а тесты читает из рабочей папки. Для сравнения исторических PR нужен checkout соответствующей ревизии без локальных правок к приложению.

## Сравнение на PR в staging

На Windows с Node 24.22.1 и Vitest 4.1.12 запускали обе команды последовательно на каждом squash-коммите, с его первым родителем в качестве базы. Локальные зависимости брали из текущей установки `staging`. Перед замером генерировали Prisma Client для соответствующей ревизии и иконки, чтобы исходный `site.webmanifest` имел те же окончания строк, что и при генерации тестом. Подготовка, установка зависимостей и сборка в замер не входят. Оба режима ограничивали `VITEST_MAX_WORKERS=2` из-за доступной памяти на машине. Число файлов включает пять проверок скриптов на `node:test`.

Сравнивали коммиты [#92](https://github.com/Clever-Agency/Gift-list/pull/92) `32fbf05c0c9db8a71cd89e9ba4a38f230aeeb954`, [#97](https://github.com/Clever-Agency/Gift-list/pull/97) `63bfc2624a68e68ecd46f9a1659e9ad8ecb68210` и [#112](https://github.com/Clever-Agency/Gift-list/pull/112) `e479f7e73f029799e1c1dff6ddd635133b460375`.

| PR | `test:affected`, файлов / время | `npm test`, файлов / время |
| --- | ---: | ---: |
| #92 — проверка смены имени на сервере | 68 / 46,05 с | 258 / 294,79 с |

Все шесть прогонов успешны. Выборочный запуск сократил время примерно на 84% в #92 и на 97% в #97. В #112 шаг выбрал полный набор из-за изменений в `.github/workflows/` и общих пакетах. Разница времени двух полных прогонов относится к одному замеру.

## Включение в CI

После локальных замеров согласовали выборочный режим для PR в `staging`. `ci.yml` использует SHA целевой ветки из события PR и глубину checkout 2 для доступа к родителям merge-коммита. При недоступной базе применяется полный набор. PR в `main` и push в `staging` или `main` запускают `npm test`. Все проверки остаются в задаче `check`.

Событие `edited` позволяет повторно выбрать режим при смене целевой ветки. Локально проверили выбор команды для PR в обе ветки, push и отсутствующего SHA. На синтетическом merge-коммите с границей shallow на его родителях Git нашёл базу и вернул только файлы PR.
