## Intent

При выходе или смене аккаунта открытый вишлист должен сразу скрыть выдачу предыдущего зрителя и загрузить список для текущей сессии. Тест профиля друга должен подтвердить, что «Обо мне» скрывается сразу после подтверждения удаления и возвращается при ошибке запроса.

</frozen-after-approval>

## Согласованная доработка

Вход, регистрация и явный выход в одной вкладке меняют общую серверную сессию браузера. Соседняя вкладка должна узнать о событии, скрыть прежние карточки и запросить данные с действующей cookie. Событие служит сигналом для повторного чтения. Периодическая проверка истечения сессии без действий пользователя — отдельное поведение.

## Карта кода

- `apps/mobile/src/session/auth-context.tsx` сообщает остальным вкладкам об успешном входе, регистрации и выходе. При входящем сигнале провайдер переходит в загрузку и читает `/api/v1/me`. Ответы устаревших запросов отбрасываются. Изменение имени, ника или настроек текущего пользователя не требует рассылки.
- `apps/mobile/src/platform/session-events.ts` передаёт пустой сигнал между вкладками одного origin через `BroadcastChannel`. При отсутствии этого API используется событие `storage`. Токен и профиль остаются в существующем контуре авторизации. На телефоне `session-events.native.ts` оставляет обновления сессии локальными.
- `apps/mobile/app/(link)/wishlist/[token].tsx` начинает чтение при смене зрителя. Ответ предыдущего запроса теряет силу, в том числе если два события о смене аккаунта пришли подряд.

## Порядок и приёмка

1. В `apps/mobile/src/session/auth-context.test.tsx` закрепить, когда публикуется событие и как принимающая вкладка переходит через загрузку к актуальной сессии. Для отложенного чтения проверить, что прежний ответ не заменяет нового зрителя.
2. Подключить сигнал в общую сессию с платформенным адаптером. Ошибка входа или выхода сохраняет текущий экран.
3. В браузере открыть один список с PUBLIC- и FRIENDS-карточкой в двух вкладках. При выходе друга в первой убедиться, что вторая скрывает FRIENDS и показывает гостевую выдачу без ручного обновления. При входе другим пользователем во второй вкладке должен появиться список, разрешённый этому пользователю.
4. Повторить тесты профиля и открытого списка, проверку типов, ESLint и сборку веб-клиента.

## Implementation Notes

- Открытая ссылка находится в группе `(link)` под общим `AuthProvider`. В `AppFrame` смена состояния меняет навигационные элементы вокруг стека. Сам публичный маршрут допускает гостя. При истечении сессии экран сам вызывает `signOut`, сохраняя адрес. Кнопка выхода вручную находится на другом экране, а вход вызывает `setUser`.
- В `apps/mobile/app/(link)/wishlist/[token].tsx` раньше загрузка зависела от токена и признака ожидания сессии. При смене одного авторизованного зрителя на другого оба значения сохранялись. Теперь состояние содержимого принадлежит паре «зритель, ссылка». Смена пары сразу убирает старые карточки и запускает чтение для текущей сессии, в том числе для гостя после выхода.
- В `public-wishlist-screen.test.tsx` используется настоящий провайдер сессии и отложенные ответы API. Проверяются выход, прямая смена аккаунта и поздний ответ. В `profile-screen.test.tsx` сценарий сетевой ошибки проверяет значение «Обо мне» до подтверждения, пока запрос выполняется и после отказа.
- Прошли 55 тестов публичного списка, 98 тестов профиля, 16 проверок маршрутов и имён компонентов, проверка типов и ESLint мобильного приложения. Expo собрал веб-клиент. Из 24 проверок скриптов первый прогон выявил расхождение CRLF/LF в сгенерированном манифесте Windows, повторный прошёл полностью.
- Chrome 158, локальный тестовый API и одинаковая навигация в двух сборках. После перехода из списка в профиль, выхода и возврата кнопкой «Назад» сборка от 26 ноября показывала гостю FRIENDS без нового чтения. Свежая сборка отправила гостевой запрос и показала только PUBLIC. Во второй вкладке, открытой на том же списке до выхода, в обеих сборках FRIENDS осталась видна даже после активации вкладки. Перезагрузка скрыла карточку. `AuthProvider` каждой вкладки хранит отдельное состояние и сейчас не получает событие из другой вкладки. Это требует пересмотра первоначального объёма правки.

## Результаты ревью

### Проверка согласованной доработки в двух вкладках

27 ноября 2026 года. Chrome 158, свежая Expo web-сборка, две вкладки одного локального origin и тестовый API с синтетическими данными. В первой вкладке использовались кнопка выхода профиля и обычная форма входа. Вторая оставалась в фоне на открытом вишлисте. URL, метка начала навигации и маркер документа сохранились.

| Действие в первой вкладке | Наблюдение во второй |
| --- | --- |
| Выход из аккаунта первого друга | После успешного DELETE повторный запрос сессии вернул 401. Пока ответ списка был задержан, прежняя карточка уже исчезла и отображалась загрузка. После ответа 200 осталась только публичная карточка. |
| Вход под другим аккаунтом | После успешного POST запрос сессии вернул второго пользователя. Следующий ответ списка показал публичную карточку и желание для второго аккаунта. Желание первого аккаунта осталось скрыто. |

На прежней сборке при тех же действиях вторая вкладка не повторяла запросы и продолжала показывать желание первого аккаунта. Проверка относится к маршруту приложения `/wishlist/:token`.

На итоговой сборке (`index-6a264b37f9f8f49c81d1e9e2f884ca0e.js`) сценарий повторён дважды. В обычном Chrome вкладки обменивались сигналом через `BroadcastChannel`. При отключении этого API до старта приложения получающая вкладка обработала ровно два сигнала `storage`, по одному на выход и вход. Оба раза старые карточки исчезли во время загрузки, а итоговый список соответствовал новой сессии.

На окончательном дереве прошли все 1 788 тестов приложения Expo (107 файлов), корневые `npm run typecheck` и `npm run lint`, экспорт веб-клиента и `git diff --check`. В том числе прошёл сценарий возврата в профиль после подтверждения нового адреса электронной почты, выявивший регрессию в промежуточном прогоне.

### Первичное ревью

- Среднее. Смоделированные смены сессии отделены от проверки обычной навигации в браузере.
- Среднее, требует проверки. Глобальный `signOut` при одновременном входе может сбросить новую сессию уже после получения ответа DELETE. Этот порядок операций существовал до исправления экрана. Условия воспроизведения записаны в `deferred-work.md`.
- Среднее. Для ссылки с `reserve` тесты подтверждают ожидание новой выдачи и проверку доступности выбранного желания после смены аккаунта.
- Низкое. Тест смены токена подтверждает, что запоздалый ответ прежней ссылки не заменяет новый список.
- Низкое. После повторного 401 гостю показываются ошибка и «Повторить». Тест проверяет ровно один DELETE и два чтения списка.

### Ревью межвкладочного обновления

| Проверка | Оценка и решение |
| --- | --- |
| Поздний ответ выхода при смене аккаунта | Среднее. Завершившийся DELETE может перезаписать новую сессию и отменить её чтение. При пересечении операций вкладке требуется сверка с cookie. |
| Одновременный вход в двух вкладках | Среднее. Тело ответа входа может быть обработано после события изменения общей cookie. Та же сверка нужна инициатору входа. |
| Детальная страница желания хранит собственные данные | Среднее. У `/gifts/[id]` отдельный экран со своим состоянием и диалогами. Он мог сохранять карточку при повторном чтении сессии ещё до этой задачи. Записано для отдельной проверки детального экрана. |
| При ошибке `/me` чтение публичного списка отправляет cookie | Претензия о раскрытии карточек прежней сессии не подтвердилась. Запрос выполняется заново, сервер фильтрует желания по действующей cookie. Уточнён комментарий о поведении экрана при неизвестном состоянии сессии. |
| Нет уведомления при отсутствии BroadcastChannel | Среднее. Обнаружен браузерный путь без обновления списка. Учтён при выборе транспорта между вкладками. |
| Удаление токена из SecureStore одновременно с новым входом | Требует проверки на устройстве. Выявленный порядок операций относится к существующему нативному хранилищу. Зафиксирован в отложенной проверке конкурентного входа и выхода. |
| Автотест подменял транспорт событий | Среднее. Регрессия в формате события могла оставить карточку в принимающей вкладке. Добавлена проверка доставки до открытого списка. |
| Код ошибки выхода подменялся признаком сетевой ошибки | Низкое. Отказ API должен сохранять причину и соответствующий текст ошибки в интерфейсе. |
| Ревью граничных случаев повторно выявило отсутствие запасного транспорта | Среднее. Тот же случай отсутствия уведомления между вкладками. |
| Ревью покрытия повторно выявило разрыв между транспортом и экраном | Среднее. Тот же тест доставки события до смонтированного списка. |
| Не проверяли позднее сохранение профиля при уже активном другом аккаунте | Низкое. Добавлена проверка сохранения пользователя B при запоздалом результате для A. |
