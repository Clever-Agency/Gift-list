# Gift List - Epic Breakdown

## Overview

Этот документ — разбор эпиков и историй для **Gift List MVP** после правок 2026-10-28 (D-20…D-42). Документы на русском.

Главные правила разбора:

- **Один клиент на три платформы (D-40, ред. 2).** Полный клиент — приложение Expo, одна кодовая база для Android, iOS и браузера (react-native-web). В браузере есть всё, кроме книги контактов. Выход iOS в App Store — шаг публикации, не разработки: истории не делятся на «до iOS» и «после».
- **Next.js — сервер и несколько своих страниц (D-40).** `api/v1`, cron, Better Auth; страницы, которым нужен серверный рендер или которые живут без сессии: `/l/:token` для анонима и превью ссылки, `/i/:token`, `/unsubscribe/:token`, `/admin`, `.well-known`. Всё остальное в браузере — веб-сборка Expo на том же домене (AD-26).
- **Один сервер, одна логика (AD-1, AD-17).** Приложение на всех платформах вызывает `app/api/v1`; Next-страницы и админка — Server Actions. Оба адаптера зовут одни и те же use-case.
- **Монорепозиторий (D-41, AD-26):** `apps/web`, `apps/mobile`, `packages/contracts`.

У каждой истории есть строка **Клиент:** `приложение` (Expo: Android, iOS и браузер; где браузер ведёт себя иначе, это сказано в AC), `Next.js` (серверная страница или админка) или `сервер`.

**Режим:** coordinator-autonomous — входы и locked-решения подтверждены Sergey.

## Requirements Inventory

### Functional Requirements

**MVP (Раунд 1):**

- FR-1: Регистрация (email, пароль, имя, Ник) → сессия и один пустой вишлист; телефон, ДР и пол не спрашиваются (D-21)
- FR-2: Вход и выход; неверный пароль не раскрывает существование email
- FR-3: Сброс пароля по одноразовой email-ссылке; одинаковый ответ для неизвестного email
- FR-5: Ник: уникален без учёта регистра; после смены `/u/{старый}` → не найден; ссылка вишлиста не ломается (A-26)
- FR-6: Поиск любого пользователя по Нику/имени; не возвращает `hideFromSearch`; пустой результат — empty state
- FR-7: Профиль `/u/{ник}`: желания по отношению (друг — PUBLIC+FRIENDS; подписчик и ContactMatch — PUBLIC; иначе без желаний); блок и несуществующий ник → не найден
- FR-8: «Не показывать в поиске»; прямые `/u/` и `/l/` работают по правилам
- FR-9: Ровно один вишлист при регистрации, одна ссылка, второго списка нет (D-23)
- FR-10: CRUD желания (название, описание, опц. цена с валютой, опц. URL); видимость меняется только у `открыт`; удаление и правка забронированного — с уведомлением держателя ✉︎
- FR-11: Просмотр по VisibilityPolicy; скрытые не отдаются и не считаются; владелец видит всё, включая SECRET
- FR-12: Статусы `открыт` / `забронирован` / `закрыт` одинаковы для всех зрителей; имя держателя — по D-13
- FR-13: Приглашение в друзья; без дубликатов pending; при дружбе — no-op
- FR-14: Принятие/отклонение; после принятия оба видят FRIENDS; повтор после отказа ≥ 24 ч (A-16)
- FR-15: Друзья, входящие и исходящие заявки; empty states
- FR-17: Бронь «куплю сам» только `единичного`, OPEN→RESERVED со Сроком (+7 по умолчанию, ≤ +30) и переключателями; снятие держателем и владельцем; гонка — один успех (D-12)
- FR-23: Удаление из друзей → FRIENDS сразу скрыты с обеих сторон; брони по A-14
- FR-24: Блок/разблок → взаимная невидимость; дружба и подписки рвутся; заявки через блок запрещены
- FR-25: «Мои брони»: Срок, фаза, «Купил», переключатели; продлить / Купил / Подарил / снять; reservation card после потери видимости
- FR-26: In-app события и email по событиям брони, датам и сроку желания; без утечки скрытого и держателя
- FR-27: `/l/{token}`: аноним видит PUBLIC без входа; бронь после регистрации; друг видит ещё FRIENDS; пусто → empty state; невалидный token и блок → не найден

- FR-32: Закрытие владельцем из открыт/забронирован; отмена 10 с; «Получено»; «Хочу ещё такой»

### NonFunctional Requirements

- NFR-1 (Корректность состояний): ≤ 1 активная бронь на желание при конкуренции; цель пилота — 0 двойных «куплю сам» (SM-2); брони с «Купил» / «Подарил» не снимаются автоматически
- NFR-2 (Безопасность): защищённые сессии (в браузере — httpOnly cookie того же домена; на Android и iOS — bearer в SecureStore); авторизация на уровне объекта
- NFR-3 (Приватность): FRIENDS и SECRET не утекают через API, поиск, ссылку и уведомления; скрытые не объясняются и не считаются; идентичность держателя не уходит владельцу без согласия (FR-31); чужие номера не хранятся (AD-18)
- NFR-4 (Производительность): открытие Профиля/вишлиста < 2 с на 4G при ≤ 100 желаниях (ориентир)
- NFR-5 (Доступность): в браузере — WCAG 2.2 AA на ключевых потоках; на Android и iOS — подписи для TalkBack и VoiceOver, размер касания, контраст токенов
- NFR-6 (Наблюдаемость): аудит смены Gift.status (actor, from→to, at)

**FRs covered:** FR-44 (модерация), FR-49

### Story 7.1: День рождения в Профиле

Клиент: приложение.

As a пользователь,

**When** получатель открывает ссылку без входа или почтовый клиент шлёт POST

### Story 7.3: Напоминание дарителю о ДР Друга (T-14)

As a даритель,

**Acceptance Criteria:**

**And** автотесты: нет открытых → нет письма; скрытый ДР → нет; Block → нет; повтор → одно; два ДР в день → один дайджест

## Epic 8: Телефон и книга контактов

### Story 8.1: Телефон в профиле и сверка книги контактов

Клиент: приложение на Android и iOS; в браузере — только свой номер (сервер — `api/v1`).

As a пользователь,
I want указать свой номер и найти знакомых по книге контактов,

**Then** он нормализуется в E.164 (страна обязательна); сохраняются `phoneE164` (unique) и `phoneHmac` = HMAC-SHA256(pepper, e164); вход по номеру невозможен (D-21)

**When** пользователь разрешает доступ к контактам (`expo-contacts`)
**Then** приложение отправляет только канонические номера; сервер считает HMAC, ищет `phoneHmac` и отвечает только найденными пользователями
**And** сырые номера запроса не пишутся ни в БД, ни в логи (AD-15-12); pepper — только env
**And** для каждого найденного создаётся `ContactMatch(scannerId, foundUserId)` без телефона; он даёт PUBLIC и дружбу не создаёт (D-30)

**When** доступ запрещён
**Then** экран объясняет и предлагает поиск по нику; приложение работает дальше
**Given** браузер
**Then** свой номер указать можно; экран «Найти знакомых» объясняет, что сверка есть в приложении на телефоне, и предлагает поиск по нику
**And** удаление номера удаляет `phoneE164` и `phoneHmac`
