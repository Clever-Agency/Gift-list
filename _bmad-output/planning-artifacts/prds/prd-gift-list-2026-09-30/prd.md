# PRD: Gift List

*Рабочее название — подтвердить позже. См. [ASSUMPTION: A-15].*

## 0. Назначение документа

Этот PRD фиксирует продуктовую спецификацию **Gift List** для PM, UX и последующих этапов BMAD (`bmad-ux`, `bmad-architecture`, `bmad-create-epics-and-stories`). Документ опирается на [Product Brief](../briefs/brief-gift-list-2026-09-29/brief.md): принятые решения брифа **не переоткрываются**; открытые вопросы брифа закрыты явными **допущениями** (`[ASSUMPTION]`). Структура: глоссарий → возможности с FR → метрики и индекс допущений. Код и архитектура **вне** этого документа.

**Раунды поставки** ([ASSUMPTION: A-24]):

| Раунд | Что входит |
|-------|------------|
| **Раунд 1 — первый запуск** | Аккаунт, два Списка, дружба, обнаружение, бронь «куплю сам», закрытие подарка Владельцем. **Без оплаты.** |
| **Раунд 2** | Полная оплата, частичный Сбор с прогрессом, провайдер, возвраты, взаимоисключение Сбора и Брони. |

Целевая модель брифа (три Действия подарка + взаимоисключение) остаётся продуктовой целью; в Раунде 1 из Действий доступна только **бронь «куплю сам»** (и закрытие Владельцем).

## 1. Видение

Gift List — веб-сервис персональных вишлистов, где владелец разделяет желания на два списка с разной видимостью и приглашает друзей **внутри сервиса**. Дарители координируются вокруг подарков без двойной покупки и без Excel в чатах.

На первом запуске координация идёт через **бронь «куплю сам»** и прозрачные статусы. Полная оплата и совместный сбор с прогрессом — следующий раунд, без ломки модели видимости и дружбы.

Продукт нужен узкому кругу (Sergey и близкие) как единый источник правды: что актуально, что занято, кто за что отвечает. Честное преимущество — дисциплина видимости и состояний подарка.

## 2. Целевой пользователь

### 2.1 Jobs To Be Done

- **Функционально (владелец):** описать желания (цена — ориентир), отделить «для всех, кто найдёт» от «только для друзей», пригласить нужных людей и не разруливать дубли руками.
- **Функционально (даритель, Раунд 1):** за один заход понять доступные подарки и забронировать «куплю сам» так, чтобы статус был однозначен для остальных.
- **Функционально (даритель, Раунд 2+):** дополнительно оплатить целиком или скинуться с видимым прогрессом.
- **Эмоционально:** снизить стресс и обиды; чувство «мы не перебиваем друг друга».
- **Социально:** координация без выкладывания всего желаемого в общий чат и без телефонной книги устройства.

### 2.2 Не-пользователи (Раунд 1)

- Магазины и маркетплейсы как продавцы внутри сервиса.
- Организаторы массовых публичных реестров (свадьбы на сотни гостей как B2B-сценарий).
- Пользователи, ожидающие только нативное приложение без веба.
- Сценарии «импорт всей телефонной книги как основа дружбы».
- Дарители, которым нужна **оплата внутри сервиса** уже на первом запуске — это Раунд 2.

### 2.3 Ключевые пользовательские сценарии

- **UJ-1. Сергей готовит два списка к дню рождения.** *(Раунд 1)*
  - **Персона + контекст:** Сергей, владелец, хочет разделить «можно всем» и «только своим».
  - **Вход:** зарегистрирован, на вебе.
  - **Путь:** создаёт подарки → относит часть в Discoverable-список, часть в Friends-only → копирует Ссылки на списки при необходимости → отправляет приглашения в друзья → проверяет, что до принятия Friends-only им не виден.
  - **Кульминация:** оба списка заполнены; ссылки на списки доступны к копированию; хотя бы одно приглашение принято; друзья видят закрытый список.
  - **Резолюция:** ждёт брони дарителей; статусы обновляются без микроменеджмента.
  - **Крайний случай:** приглашённый отклоняет — Friends-only остаётся скрыт.

- **UJ-2. Марина принимает дружбу и бронирует Friends-only подарок.** *(Раунд 1)*
  - **Персона + контекст:** Марина — близкая подруга; до принятия не видела закрытый список.
  - **Вход:** есть аккаунт; открыла приглашение.
  - **Путь:** принимает дружбу → видит Friends-only → выбирает открытый подарок → жмёт «куплю сам».
  - **Кульминация:** подарок `забронирован`; другие видят, кто взял; повторная бронь недоступна.
  - **Резолюция:** покупает вне сервиса; Сергей позже закрывает подарок как полученный.
  - **Крайний случай:** Дима параллельно жмёт «куплю сам» — успешен только один.

- **UJ-3. Коллега открывает Discoverable-список по ссылке на список и бронирует подарок.** *(Раунд 1)*
  - **Персона + контекст:** Алексей не в друзьях; получил **ссылку на Discoverable-список** (не на профиль).
  - **Вход:** может быть без сессии → регистрируется/входит → снова открывает ту же ссылку на список.
  - **Путь:** видит **только этот Список и его Подарки** (не Friends-only, не обязан заходить в Профиль) → бронирует открытый подарок.
  - **Кульминация:** подарок занят; Friends-only по-прежнему скрыт.
  - **Резолюция:** Алексей не получает доступ к Friends-only без принятого приглашения. Профиль `/u/{ник}` остаётся отдельным способом найти человека.

- **UJ-3b. Марина открывает Friends-only по ссылке на список.** *(Раунд 1)*
  - **Путь:** принятый Друг переходит по ссылке на Friends-only-список → видит только этот Список и Подарки.
  - **Крайний случай:** аутентифицированный не-друг открывает ту же ссылку → **не** видит Подарков, а видит ясное объяснение, что список доступен только людям из списка друзей Владельца (не пустая страница и не «не найдено»). Аноним → сначала вход; после входа, если не Друг — то же объяснение.

- **UJ-4. Дима снимает свою бронь.** *(Раунд 1)*
  - **Путь:** открывает «Мои брони» или карточку подарка → снимает бронь → статус снова `открыт`.

- **UJ-5. Бывший друг теряет Friends-only при активной брони.** *(Раунд 1)*
  - **Путь:** дружба разорвана → Подарки Friends-only больше не видны; по Ссылке на этот Список — объяснение «только для друзей» (FR-27), не «не найдено» → бронь Димы сохраняется и управляется через «Мои брони» (A-14).

- **UJ-6. Марина скидывается на подарок (Сбор).** *(Раунд 2 — не первый запуск)*
  - После включения оплаты: частичный взнос, видимый прогресс, «куплю сам» недоступно на время Сбора. См. FR-16, FR-18–FR-22.

## 3. Глоссарий

- **Владелец** — пользователь, которому принадлежат Списки и Подарки.
- **Даритель** — пользователь, который видит Подарок и может выполнить доступное Действие подарка (не обязательно Друг).
- **Профиль** — публично находимая карточка пользователя (ник, отображаемое имя, ссылка `/u/{ник}`).
- **Ник** — уникальный идентификатор пользователя в сервисе (латиница/цифры/допустимые символы — уточняется в UX).
- **Discoverable-список** — Список Владельца, видимый любому аутентифицированному пользователю, который открыл **Ссылку на список** этого Списка или нашёл Профиль Владельца.
- **Friends-only-список** — Список Владельца, видимый только принятым Друзьям Владельца (в т.ч. по **Ссылке на список** этого Списка).
- **Список** — один из двух контейнеров Подарков Владельца (Discoverable или Friends-only). У каждого Владельца ровно два Списка.
- **Ссылка на список** — отдельный URL каждого из двух Списков Владельца, отличный от ссылки Профиля `/u/{ник}` (решение D-11). При достаточном праве доступа открывает **только этот Список** и его Подарки; при Friends-only без Дружбы — экран-объяснение без Подарков (не «не найдено»). Не является ссылкой на отдельный Подарок.
- **Подарок** — позиция в Списке: название, описание, опциональная цена-ориентир, Статус подарка.
- **Статус подарка (Раунд 1)** — одно из: `открыт` | `забронирован` | `закрыт`.
- **Статус подарка (Раунд 2+)** — добавляется `сбор`.
- **Действие подарка (цель продукта)** — полная оплата; бронь «куплю сам»; частичный взнос. В Раунде 1 доступна только бронь «куплю сам» (+ закрытие Владельцем).
- **Сбор** — *(Раунд 2)* режим Подарка с частичными взносами до полной суммы.
- **Бронь («куплю сам»)** — режим, в котором Даритель обязался купить Подарок сам (вне сервиса в Раунде 1).
- **Дружба** — взаимная связь in-service после Приглашения и Принятия: любой аутентифицированный пользователь может пригласить другого; после принятия **оба** видят Friends-only друг друга (решение D-10).
- **Приглашение** — запрос на Дружбу от любого аутентифицированного пользователя к другому; до Принятия Friends-only-списки обеих сторон друг другу **не видны**.
- **Прогресс сбора** — *(Раунд 2)* доля/сумма собранного относительно Цены.
- **Взнос** — *(Раунд 2)* успешный частичный платёж в Сбор.
- **Закрытие** — переход в `закрыт`. В Раунде 1 — подтверждение Владельцем после Брони (или снятие/таймаут Брони без закрытия). В Раунде 2 — также после полной оплаты или завершения Сбора.

## 4. Возможности

### 4.1 Учётная запись и вход

**Описание:** Даритель и Владелец работают только из аутентифицированной сессии. Реализует UJ-1–UJ-3.  
[ASSUMPTION: A-1] Регистрация и вход — **email + пароль**.  
[ASSUMPTION: A-2] В Раунде 1 подтверждение email **желательно**, но **не блокирует** бронь «куплю сам»; денежные действия в Раунде 2 требуют подтверждённого email. Просмотр Discoverable — после входа.  
[ASSUMPTION: A-3] Восстановление доступа — ссылка сброса пароля на email.  
[ASSUMPTION: A-4] В Раунде 1 самодекларация возраста **не обязательна** (нет платежей). В Раунде 2 — **18+** перед денежными действиями. OAuth и вход через телефон **вне** Раунда 1.

**Functional Requirements:**

#### FR-1: Регистрация по email

Пользователь может создать аккаунт с email, паролем, отображаемым именем и Ником. Realizes UJ-1, UJ-3.

**Consequences (testable):**
- Система отклоняет регистрацию с уже занятым email или Ником.
- После регистрации пользователь аутентифицирован и попадает в свой пустой вишлист (два Списка без Подарков).

#### FR-2: Вход и выход

Пользователь может войти по email/паролю и завершить сессию.

**Consequences (testable):**
- Неверный пароль не открывает сессию и не раскрывает, существует ли email.
- Выход инвалидирует текущую сессию на этом клиенте.

#### FR-3: Сброс пароля

Пользователь может запросить сброс пароля на email и задать новый пароль по одноразовой ссылке.

**Consequences (testable):**
- Ссылка сброса одноразовая и ограничена по времени.
- Запрос сброса для неизвестного email не раскрывает факт отсутствия аккаунта в UI (одинаковый ответ).

#### FR-4: Подтверждение email (Раунд 2 — gate на платежи)

Пользователь с неподтверждённым email не может инициировать полную оплату или Взнос. *(Вне Раунда 1.)*

**Consequences (testable):**
- При попытке оплаты UI объясняет необходимость подтверждения и предлагает повторно отправить письмо.
- Бронь «куплю сам» допускается без подтверждённого email.

### 4.2 Обнаружение пользователя, Профиль и Ссылки на списки

**Описание:** Человека находят по нику, поиску и ссылке Профиля; конкретный Список открывают по **Ссылке на список** — без телефонной книги. Realizes UJ-3, UJ-3b.  
[ASSUMPTION: A-5] У каждого пользователя обязательный уникальный **Ник**.  
[ASSUMPTION: A-6] Есть **поиск** по Нику (точное/префиксное совпадение) и по отображаемому имени (нечёткий поиск с лимитом выдачи).  
[ASSUMPTION: A-7] У Профиля есть **публичная ссылка** вида `/u/{ник}`; по ней аутентифицированный пользователь открывает Профиль и может увидеть Discoverable-список. Профиль **не удаляется** и остаётся способом найти человека.  
[ASSUMPTION: A-25] Точный path/token **Ссылки на список** (отличный от `/u/{ник}`) выбирается в architecture; продуктово у каждого из двух Списков свой стабильный URL.

**[DECISION: D-11] Ссылки на списки (подтверждено Sergey; Friends-only-уточнение):**
- У каждого из двух Списков (Discoverable и Friends-only) есть **своя** Ссылка на список, отдельная от `/u/{ник}`.
- Открытие Ссылки на список относится **только к этому Списку**; второй Список не показывается; проход через Профиль **не требуется**.
- **Discoverable-ссылка** (без изменений): любой **аутентифицированный** пользователь с ссылкой видит Подарки; анонимный — призыв войти, без Подарков до входа.
- **Friends-only-ссылка:**
  - принятый Друг видит Список и Подарки;
  - аутентифицированный **не-друг** **не** видит Подарков; видит **ясное объяснение**, что список доступен только людям из списка друзей Владельца (точная формулировка — UX; требование — объяснение, **не** пустая страница, **не** «не найдено», **не** Подарки);
  - анонимный посетитель — призыв войти, без Подарков; после входа, если не Друг — то же объяснение, что у не-друга.
- Это **не** ссылка на отдельный Подарок.
- Владелец может **скопировать** Ссылку на список; полноценный share-sheet **вне** scope — достаточно наличия ссылки и копирования.
- Ссылка Профиля `/u/{ник}` сохраняется.

**Functional Requirements:**

#### FR-5: Назначение и смена Ника

Пользователь может задать Ник при регистрации и сменить его позже с проверкой уникальности.

**Consequences (testable):**
- Ник уникален в системе без учёта регистра.
- После смены старая ссылка `/u/{старый-ник}` не открывает Профиль (или отдаёт «не найдено»).
- Ссылки на списки **не зависят** от смены Ника (остаются валидными) — [ASSUMPTION: A-26].

#### FR-6: Поиск пользователей

Аутентифицированный пользователь может найти других по Нику или отображаемому имени.

**Consequences (testable):**
- Поиск не возвращает пользователей, скрывших Профиль из поиска (FR-8); по прямой ссылке Профиль и Ссылки на списки (с учётом видимости) остаются доступны.
- Пустой результат показывает понятное пустое состояние, не ошибку.

#### FR-7: Профиль по ссылке

Аутентифицированный пользователь может открыть Профиль по `/u/{ник}` и увидеть Discoverable-список Владельца (как способ найти человека). Realizes UJ-3 (альтернативный вход).

**Consequences (testable):**
- Friends-only-список на Профиле **не отображается**, если зритель не принятый Друг.
- Несуществующий ник → «пользователь не найден».
- Профиль не заменяет Ссылку на список: для шаринга конкретного Списка используется FR-27 / FR-28.

#### FR-8: Опция «не показывать в поиске»

Владелец может запретить появление Профиля в поиске, сохранив доступ по ссылке Профиля, по Ссылкам на списки (с правилами видимости) и для Друзей.

**Consequences (testable):**
- При включённой опции поиск не возвращает этого пользователя.
- `/u/{ник}` и Ссылки на списки продолжают работать по своим правилам доступа.

#### FR-27: Открытие Списка по Ссылке на список

Пользователь может открыть Ссылку на список без обязательного перехода в Профиль и без показа второго Списка. При достаточном праве — видит **только** этот Список и его Подарки. Realizes UJ-3, UJ-3b.

**Consequences (testable):**
- **Discoverable:** аутентифицированный посетитель с ссылкой видит Подарки этого Списка; анонимный — только призыв войти/зарегистрироваться, без Подарков.
- **Friends-only + принятый Друг:** видит Подарки этого Списка.
- **Friends-only + аутентифицированный не-друг:** Подарки **не** показываются; показывается **объяснение**, что список виден только людям из списка друзей Владельца (не blank, не «список не найден», не названия/состав Подарков).
- **Friends-only + анонимный:** призыв войти, без Подарков; после успешного входа, если пользователь не принятый Друг — то же объяснение, что у не-друга.
- На экране по Ссылке на список **не** отображается другой Список Владельца.
- Невалидная/несуществующая ссылка → «список не найден» (это состояние **не** используется для отказа не-другу по валидной Friends-only-ссылке).
- Ссылка ведёт на Список целиком, не на карточку одного Подарка.

#### FR-28: Копирование Ссылки на список Владельцем

Владелец может скопировать Ссылку на список для каждого из своих двух Списков (например, в буфер обмена).

**Consequences (testable):**
- Для Discoverable и для Friends-only доступны разные URL.
- После копирования ссылка пригодна к открытию по FR-27.
- Полноценный системный share-sheet / превью в мессенджерах **не требуется** в Раунде 1.

### 4.3 Списки и Подарки (CRUD)

**Описание:** У Владельца ровно два Списка. Realizes UJ-1. Цена в Раунде 1 — **информационный ориентир** (не платёжный инвариант).

**Functional Requirements:**

#### FR-9: Два Списка по умолчанию

Система создаёт Discoverable-список и Friends-only-список при регистрации; Владелец не удаляет их, только наполняет. Для каждого Списка существует Ссылка на список (D-11).

**Consequences (testable):**
- У каждого аккаунта ровно два Списка этих типов.
- Нельзя создать третий Список в Раунде 1.
- У каждого из двух Списков есть своя Ссылка на список с момента создания Списков.

#### FR-10: Создание и редактирование Подарка

Владелец может создать, изменить и удалить Подарок: название, описание, опциональная цена (≥ 0), опциональная URL-ссылка на товар.

**Consequences (testable):**
- Подарок всегда принадлежит ровно одному Списку.
- Владелец может перенести Подарок между Списками, только если Статус = `открыт`.
- Удаление Подарка в статусе `забронирован` требует подтверждения; активная Бронь снимается с уведомлением бронировавшего.

#### FR-11: Просмотр Списков по правилам видимости

Даритель видит только те Списки и Подарки, на которые у него есть право (через Профиль, дружбу или Ссылку на список — FR-27).

**Consequences (testable):**
- Не-друг видит Discoverable (Профиль или Discoverable-ссылка); Подарки Friends-only не видит. По валидной Friends-only-ссылке — объяснение «только для друзей» (FR-27), а не отсутствие экрана / «не найдено».
- На Профиле Friends-only по-прежнему **не показывается** не-другу как список (отдельный от Ссылки на список случай).
- Принятый Друг видит оба Списка Владельца (и по навигации, и по соответствующим Ссылкам на списки).
- Владелец всегда видит оба своих Списка и статусы.

#### FR-12: Отображение Статуса подарка

Все, кто видит Подарок, видят одинаковый Статус подарка. В Раунде 1 Прогресс сбора **не показывается** (нет Сбора).

**Consequences (testable):**
- Статусы `открыт` / `забронирован` / `закрыт` однозначны в UI.
- [ASSUMPTION: A-8] *(Раунд 2)* Имена вкладчиков в прогрессе Сбора видны зрителям Подарка.

### 4.4 Дружба in-service

**Описание:** Дружба — единственный допуск к Friends-only. Не телефонная книга. Realizes UJ-1, UJ-2, UJ-5.

**[DECISION: D-10] Взаимная дружба (подтверждено Sergey, закрывает Q-4 / бывш. A-10):**
- Любой аутентифицированный пользователь может отправить Приглашение другому.
- После принятия **оба** видят Friends-only-списки **друг друга**.
- До принятия Friends-only остаётся скрытым.
- Это **заменяет** формулировку брифа «только владелец списка приглашает».

**Functional Requirements:**

#### FR-13: Отправка Приглашения

Пользователь A может отправить Приглашение пользователю B из Профиля B или из поиска.

**Consequences (testable):**
- Пока Приглашение не принято, B **не видит** Friends-only A (и наоборот).
- Повторное Приглашение при pending не создаёт дубликат; при уже Дружбе — no-op с пояснением.
- B может отклонить; A получает статус «отклонено».

#### FR-14: Принятие и отклонение

B может принять или отклонить входящее Приглашение.

**Consequences (testable):**
- После принятия оба видят Friends-only друг друга.
- Отклонённое Приглашение не даёт доступа; A может отправить новое не раньше, чем через [ASSUMPTION: A-16] **24 часа**.

#### FR-15: Список друзей и входящих

Пользователь видит своих Друзей, исходящие pending и входящие Приглашения.

**Consequences (testable):**
- Пустые состояния для «нет друзей» и «нет заявок» покрыты в UI.

### 4.5 Действия на Подарке (Раунд 1: только бронь)

**Описание:** В Раунде 1 единственное Действие дарителя — бронь «куплю сам». Полная оплата, Сбор и взаимоисключение с Сбором — Раунд 2 (цель брифа сохраняется). Realizes UJ-2–UJ-4.

**Functional Requirements:**

#### FR-16: Полная оплата — *Раунд 2*

Даритель может оплатить Цену целиком; после успеха Статус = `закрыт`. *(Вне первого запуска.)*

**Consequences (testable):**
- После закрытия Действия недоступны.
- Одновременные попытки: успешна только одна.

#### FR-17: Бронь «куплю сам» — *Раунд 1*

Даритель может забронировать Подарок в статусе `открыт`; Статус → `забронирован`.

**Consequences (testable):**
- Бронь недоступна, если Статус = `закрыт` или уже `забронирован` (в Раунде 2 — также если `сбор`).
- Бронирующий может снять свою Бронь → `открыт`.
- [ASSUMPTION: A-23] Имя держателя Брони **видно** Владельцу и всем, кто видит Подарок.
- [ASSUMPTION: A-9] Владелец может снять чужую Бронь; Бронь автоматически снимается через **14 суток** без закрытия, с уведомлением бронировавшего. Закрытие по Брони подтверждает **Владелец** («получил / можно закрыть»). Опциональная отметка Дарителя «купил» не закрывает Подарок сама.

#### FR-18: Частичный Взнос и Сбор — *Раунд 2*

Даритель вносит часть цены; первый Взнос → `сбор`; при полной сумме → `закрыт`. Пока `сбор` — «куплю сам» недоступно; пока Бронь — взносы недоступны. *(Вне первого запуска.)*

**Consequences (testable):**
- Прогресс сбора виден всем, кто видит Подарок.
- Взаимоисключение с Бронью соблюдается (FR-19).

#### FR-19: Взаимоисключение Сбора и Брони — *Раунд 2*

Система гарантирует невозможность одновременной активной Брони и активного Сбора. *(В Раунде 1 Сбора нет — инвариант сводится к единственной активной Брони на Подарок.)*

**Consequences (testable):**
- Раунд 1: два параллельных «куплю сам» — успешен только один.
- Раунд 2: попытка нарушить взаимоисключение получает отказ с понятной причиной.

### 4.6 Платежи, валюта, возвраты — *весь раздел = Раунд 2*

**Описание:** На первом запуске **нет** платёжного провайдера, холдов, выводов и возвратов. Ниже — зафиксированные допущения для следующего раунда (не реализовывать в Раунде 1).  
[ASSUMPTION: A-24] Первый запуск — **без оплаты**; весь платёжный функционал отложен на Раунд 2.  
[ASSUMPTION: A-17] Провайдер Раунда 2 — **ЮKassa**.  
[ASSUMPTION: A-18] Валюта — **RUB** only.  
[ASSUMPTION: A-19] Средства холдируются/учитываются до Закрытия, затем к выводу Владельцу.  
[ASSUMPTION: A-20] Комиссию платит Даритель.  
[ASSUMPTION: A-21] Вывод вручную после Закрытия; без авто-payout на каждый взнос.

**Functional Requirements (Раунд 2):**

#### FR-20: Инициация платежа — *Раунд 2*

Даритель начинает полную оплату или Взнос у провайдера.

#### FR-21: Подключение выплат Владельца — *Раунд 2*

Владелец подключает выплатной метод; без него вывод блокируется с понятным статусом.

#### FR-22: Возвраты — *Раунд 2*

Возвраты при отмене Сбора, удалении Подарка в `сбор`, переплате, отзыве Взноса до Закрытия. Бронь не создаёт платёжных обязательств.

### 4.7 Удаление из друзей, блок, Подарок в процессе

**Описание:** Граничные случаи приватности. Realizes UJ-5.  
[ASSUMPTION: A-11] **Удаление из друзей** — любая сторона; Friends-only сразу скрываются. Discoverable остаётся по правилам обнаружения.  
[ASSUMPTION: A-12] **Блок** — взаимная невидимость Профилей; pending отменяются; Дружба рвётся; новые Приглашения через блок запрещены.  
[ASSUMPTION: A-13] *(Раунд 2)* **Сбор в процессе** при потере видимости: взносы сохраняются; новый доступ закрыт.  
[ASSUMPTION: A-14] **Бронь в процессе** при потере видимости: сохраняется до снятия/таймаута A-9; управление через «Мои брони».

**Functional Requirements:**

#### FR-23: Удаление из друзей

Любая сторона может удалить другую из друзей.

**Consequences (testable):**
- Сразу после удаления Подарки Friends-only недоступны с обеих сторон; по Ссылке на Friends-only-список — объяснение FR-27 (не «не найдено»).
- Активные Брони обрабатываются по A-14 (Сборы — по A-13 в Раунде 2).
- Повторная Дружба только через новое Принятое Приглашение.

#### FR-24: Блокировка

Пользователь может заблокировать и разблокировать другого.

**Consequences (testable):**
- Заблокированный не видит Профиль блокирующего и наоборот.
- Нельзя отправить Приглашение через блок.
- *(Раунд 2)* Блок **не** отменяет уже сделанный Взнос автоматически.

#### FR-25: «Мои брони» (Раунд 1); «Мои взносы» — Раунд 2

Даритель видит свои активные Брони и может снять их после потери видимости Списка. Список «Мои взносы» появляется в Раунде 2.

**Consequences (testable):**
- Снять Бронь можно из этого раздела в Раунде 1.

### 4.8 Базовые уведомления (in-app)

**Описание:** Минимум, без нативных push.  
[ASSUMPTION: A-22] В Раунде 1 — **только in-app** (+ email на сброс пароля; опционально письмо подтверждения email). Платёжные письма провайдера — Раунд 2.

**Functional Requirements:**

#### FR-26: In-app события

**Раунд 1:** входящее Приглашение; принятие/отклонение; новая Бронь на Подарок Владельца; снятие Брони (в т.ч. по таймауту); запрос Владельцу подтвердить получение / Закрытие.

**Раунд 2 (дополнительно):** новый Взнос; Закрытие после оплаты/сбора.

**Consequences (testable):**
- Непрочитанные считаются бейджем.
- Уведомления не раскрывают Friends-only тем, у кого нет доступа.

## 5. Non-Goals (явно)

### Раунд 1 (первый запуск)

- **Любая оплата внутри сервиса:** полная оплата, Сбор, провайдер, холд, вывод, возвраты, комиссии.
- Нативные iOS/Android клиенты.
- Импорт телефонной книги / sync контактов ОС.
- Маркетплейс и партнёрский checkout.
- Групповые вишлисты с несколькими Владельцами.
- Анонимные Дарители без аккаунта.
- OAuth, Push/SMS, мультивалюта.
- Прогресс денежного сбора и UI взносов.
- Полноценный share-sheet / deep-link preview design (достаточно копирования Ссылки на список — FR-28).
- Ссылки на отдельный Подарок (per-gift links).

### Позже / вне продукта

- Публичные «свадебные реестры» как отдельный продукт.
- Админ-панель модерации уровня маркетплейса.
- Реализация оплаты — только в Раунде 2 по §4.5–4.6.

## 6. Scope по раундам

### 6.1 Раунд 1 — In Scope (первый запуск)

- Адаптивный веб-клиент.
- Аккаунт: регистрация/вход/сброс пароля (A-1, A-3); email confirm без жёсткого gate (A-2).
- Ник, поиск, ссылка Профиля `/u/{ник}`, скрыть из поиска.
- **Ссылки на списки** (D-11): отдельный URL на Discoverable и на Friends-only; открытие только этого Списка (FR-27); копирование Владельцем (FR-28).
- Два Списка; CRUD Подарков; статусы `открыт` / `забронирован` / `закрыт`; цена как ориентир.
- Дружба: приглашение, принятие/отклонение, удаление, блок.
- Бронь «куплю сам» + закрытие Владельцем + «Мои брони».
- In-app уведомления Раунда 1 (FR-26).

### 6.2 Раунд 2 — следующий раунд (оплата)

- FR-4 (gate email), FR-16, FR-18–FR-22.
- Статус `сбор`, прогресс, имена вкладчиков (A-8), A-13.
- ЮKassa, RUB, холд, возвраты, вывод (A-17–A-21).
- Взаимоисключение Сбора и Брони (FR-19 в полной форме).
- «Мои взносы»; платёжные уведомления.

### 6.3 Out of Scope для обоих раундов (пока)

- Нативные приложения, телефонная книга, OAuth, Push/SMS, игрофикация, лента друзей.
- Per-gift share links; полноценный share-sheet.

## 7. Платформа

- **Раунд 1+:** веб-приложение, адаптивная вёрстка (мобильный браузер — first-class).
- **Не сейчас:** нативные приложения, отдельное desktop-only приложение.
- Офлайн не требуется; при потере сети — понятная ошибка на действиях.

## 8. Cross-Cutting NFRs

- **Корректность состояний:** в Раунде 1 — не более одной активной Брони на Подарок при конкуренции; цель пилота — ноль двойных «я куплю» на один подарок.
- **Безопасность:** сессии защищены; авторизация на уровне объекта (Список/Подарок). Платёжные карты — только в Раунде 2 и только через провайдера.
- **Приватность:** Friends-only не утекает через API, поиск, уведомления; ответ по Friends-only Ссылке на список для не-друга — объяснение без названий/состава Подарков (и без маскировки под «не найдено»).
- **Производительность (ориентир):** открытие Профиля и Списка < 2 с на обычном 4G при ≤ 100 Подарках.
- **Доступность:** клавиатура на ключевых потоках, контраст, label у форм.
- **Наблюдаемость:** аудит смены Статуса подарка (в Раунде 2 — ещё платёжные события).

## 9. Ограничения: координация и доверие

- Ошибка состояния Брони дороже отсутствующей фичи оплаты на первом запуске.
- Не обещать в UI Раунда 1 оплату «скоро» как рабочую кнопку — только отсутствие денежных действий (или явная пометка «будет позже», если понадобится в копирайте).
- В Раунде 2: прозрачность взносов (A-8); блок ≠ отмена Взноса.

## 10. Success Metrics

**Primary (Раунд 1)**

- **SM-1:** На пилоте (≥ 1 событие Владельца с ≥ 3 Дарителями) доля Подарков с осмысленным исходом (бронь и/или закрытие) без конфликта «два человека купили одно» — качественный опрос; цель — «большинство». Validates FR-17, FR-19 (R1).
- **SM-2:** Подтверждённые инциденты двойной брони/покупки одного Подарка = **0**. Validates FR-17, FR-19.

**Secondary (Раунд 1)**

- **SM-3:** Владелец создаёт Подарки в обоих Списках и получает ≥ 3 принятых Дружбы без поддержки. Validates FR-9–FR-14.
- **SM-4:** Медиана от открытия видимого Подарка до успешной Брони ≤ **3 минут** на вебе. Validates UJ-2–UJ-3.

**Раунд 2 (добавятся)**

- Доля закрытий через оплату/сбор; время до успешного платежа; ноль двойных покупок с учётом Сбора.

**Counter-metrics**

- **SM-C1:** Не давить напоминаниями о брони/взносах ради «активности».
- **SM-C2:** Не максимизировать Discoverable-охват ценой утечек Friends-only.
