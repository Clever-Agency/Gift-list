# Sprint Change Proposal — 2026-11-11, видимость забронированного желания

> **Статус: утверждено (`status: approved`, 2026-11-11).** Sergey одобрил, одобрение передал Evgeniy (t353u). Нормативные правки §5 внесены этим же коммитом через `bmad-correct-course`; код и тексты каталога — S23.2–S23.3, гейты — S23.4.

## 1. Суть

**Что запустило.** CLE-82 (D6) зафиксировал расхождение: форма правки забронированного желания показывает подсказки «Нельзя менять, пока желание забронировано» и «Видимость меняется только у открытого желания», а EXPERIENCE.md в тот же момент требует других текстов и другого поведения чипа. Проверка показала, что расходится не только копирайт: правило «видимость меняется только у `OPEN`» перестало быть продуктово верным.

**Решение (продуктовое правило, дословно).** Владелец может **сужать и расширять** видимость желания в любой момент, в том числе когда желание `RESERVED`. Если после сужения держатель брони **теряет доступ по VisibilityPolicy**, бронь снимается (желание снова `OPEN`). Повторное расширение видимости бронь **не восстанавливает**. Если держатель доступ сохраняет, бронь остаётся. Перед сужением, которое снимет бронь, владелец видит confirm «Бронирующий потеряет доступ, бронь снимется» (Подтвердить / Отмена). Инфраструктуры уведомлений ещё нет (Epic 5–6): сейчас снятие **тихое**, уведомление держателю записано в `deferred-work.md`. Закрытое (`CLOSED`) и архивное желание — только просмотр; любая правка → 400; у архивного подсказка «Архивное желание можно только просматривать». `quantity` у `RESERVED` по-прежнему меняется только у `OPEN` (не менять). Старый текст блокировки видимости «Нельзя менять, пока желание забронировано» убрать.

**Тип:** изменение продуктового правила плюс исправление нормативных документов; не техническая находка. Объём MVP, порядок эпиков и набор историй не меняются — переписываются AC уже существующих Story 2.3, 2.6 и 5.4.

**Уточнения, без которых правило читается двусмысленно.**

1. **Оценка доступа держателя — фильтр желания AD-7, без исключения reservation card.** В AD-7 есть матрица A-14 / FR-25: `reservedById` при `RESERVED` всё ещё видит reservation card, даже потеряв доступ к списку (разрывы дружбы, блок). Это правило **остаётся** для потери отношения. Для смены `Gift.visibility` владельцем «есть ли доступ» считается как у обычного зрителя желания (`VisibilityPolicy` / фильтр `SECRET` / `FRIENDS` / `PUBLIC` из AD-7), **без** исключения reservation card — иначе `SECRET` никогда не снимал бы бронь. A-14 в PRD не переписывается в обратную сторону.
2. **Примеры переходов** (закрепить в §5 и позже тестами S23.2):
   - `PUBLIC → FRIENDS`, держатель — принятый друг → бронь остаётся;
   - `PUBLIC → FRIENDS`, держатель не друг (пришёл по ссылке, подписчик, контакт) → бронь снимается;
   - любой `→ SECRET` → бронь снимается;
   - `FRIENDS → PUBLIC` после снятия → бронь не возвращается;
   - смена на то же значение — no-op, как сейчас в `updateGift`.
3. **Снятие брони — через `GiftStatusService`** (AD-8: единственный writer статуса и колонок брони), в **одной транзакции** с записью новой видимости. Второго пути Prisma к `status` не появляется.
4. **Архив (`archivedAt != null`).** Сейчас `updateGift` отвечает `NOT_FOUND`, потому что в `where` стоит `archivedAt: null`. Новое правило для владельца своего архивного желания: `400 VALIDATION` и подсказка «Архивное желание можно только просматривать», а не маскировка «не найдено». Чужое по-прежнему `NOT_FOUND`. `CLOSED`: только просмотр, любая правка → 400; отдельную формулировку подсказки для `CLOSED` в этом запуске не выдумываем — форма read-only, точный ключ копирайта закроет S23.3. S23.3 закрыл: у `закрыт` и архива **одна** подсказка «Архивное желание можно только просматривать.», ключи `errors.reason.GIFT_CLOSED` и `errors.reason.GIFT_ARCHIVED` несут один и тот же текст.
5. **Уведомления.** Уведомление держателю о снятии брони из-за сужения видимости и прежняя подсказка «Желание забронировано — бронировавший получит уведомление» при правке других полей — долг Epic 5–6, записан в `deferred-work.md`. В коде уведомления не обещаются как уже работающие.
6. **Миграция БД не нужна.** Схема уже хранит `visibility`, `status` и колонки брони (AD-9); новые поля не появляются. Если в S23.2 окажется, что нужно поле для аудита причины снятия, это отдельный вопрос в отчёт, а не этот коммит.

## 4. Подход

**Прямая корректировка (Option 1).** Новое правило не требует ни новой таблицы, ни нового экрана: `visibility` уже меняется одним полем (FR-10), бронь снимается существующим переходом `RESERVED → OPEN` владельцем (AD-8/AD-9), а «есть ли у держателя доступ» уже умеет считать `VisibilityPolicy`. Меняются: условие в `updateGift`, порядок записи (видимость + снятие брони в одной транзакции через `GiftStatusService`), форма/чип у владельца, подтверждение и тексты.

**Почему не второй путь и не отдельная история брони.** Правило принадлежит желанию (видимость — поле `Gift`) и его правке (FR-10); отдельная сущность «сужение видимости» создала бы второй write-путь статуса, запрещённый AD-8. Отдельная история не нужна: меняется AC Story 2.3 и 5.4, код идёт задачами CLE-82 (S23.2–S23.4).

**Трудоёмкость:** низкая-средняя (1–1,5 дня на сервер и клиент): правка `updateGift` и preflight, один confirm, тексты каталога, тесты переходов.
