# Sprint Change Proposal — 2026-11-17, «не найдено» как HTTP 404

> **Статус: утверждено (`status: approved`, 2026-11-17).** Sergey одобрил вариант 1 (лучшая практика REST) 2026-11-17, одобрение передал Evgeniy (t434u). Нормативные правки §5 внесены этим же коммитом через `bmad-correct-course`; код и тесты — следующая подзадача (CLE-104 + CLE-103), в этом коммите их нет.

## 1. Суть

**Что запустило.** CLE-104 зафиксировал расхождение wire-контракта с REST: публичное чтение по токену и профиль по нику отвечают на «не найдено» **успехом** (`ok: true`, `access: "not_found"`), а не ошибкой. AD-12 при этом прямо называет такой ответ gate-ответом и требует «иного конверта нет». CLE-103 — следствие того же поведения в HTML: Next-страницы `/l/:token` и `/i/:token` на неизвестный токен и `Block` отдают **200** и рисуют текст «не найдено» внутри обычного каркаса, поэтому поисковик и монитор ссылок видят живую страницу.

**Решение (продуктовое правило, дословно).** Публичные эндпоинты чтения `GET /api/v1/l/…` (вишлист по токену), `GET /api/v1/i/:token` (превью приглашения) и `GET /api/v1/u/:nick` (профиль) при «не найдено» отвечают **HTTP 404** и **одним единым конвертом ошибки AD-12** `{ ok: false, code: "NOT_FOUND", message }` — без `reason`, `field` и `params`, **без подсказки о причине**: неизвестный или битый токен/ник, скрытый либо недоступный список и `Block` в любую сторону дают побайтово одинаковый ответ (статус, тело, заголовки, кроме неизбежных). Anti-enumeration сохраняется — как у GitHub для приватных репозиториев. Успешный ответ списка или профиля — только найденный: `access: "not_found"` из успешной схемы уходит. Next-страницы `/l/:token` и `/i/:token` при «не найдено» отдают **реальный HTTP 404** через `notFound()` с общим not-found UI каркаса — тот же текст из i18n и тот же общий футер; это закрывает CLE-103. Метаданные и `noindex` — как сейчас. AD-7 «Prevents: 404 как маскировка Block» переформулируется: маскировка запрещена в смысле «различимый ответ», а единый 404 для всех причин разрешён и обязателен.

**Тип:** изменение wire-контракта и HTTP-поведения публичных чтений плюс исправление нормативных документов; не техническая находка. Объём MVP, порядок эпиков и набор историй не меняются — переписываются AC существующих Story 3.2, 3.3, 3.4, 4.5, 4.7, 5.8 и сводка ARCH-R6.

**Уточнения, без которых правило читается двусмысленно.**

1. **Поле `access` в успехе остаётся.** Успешная схема теряет только ветку `not_found`, но сохраняет `access: "gifts"`. Так тело найденного списка остаётся байт-в-байт прежним, и ни один потребитель (`apps/mobile`, Next-страницы, тесты) не переписывается ради удаления одного дискриминанта. Поле с единственным значением избыточно; убрать его целиком — отдельная косметическая чистка контракта, не эта задача. Это консервативный вариант из поручения; рекомендованная там же правка «убрать ветку `not_found` из успешной схемы, остальные поля без изменений» выполнена буквально.
2. **`/u/:nick` — тот же 404, но не тот же статус для анонима.** Неизвестный ник, битый ник (сегмент с `/`, невалидный ник) и `Block` дают одинаковый 404 `NOT_FOUND`. Отсутствие сессии остаётся `UNAUTHENTICATED` (401): это не скрытая причина, а состояние вызывающего, которое он и так знает; экраны приложения не меняются.
3. **`/i/:token` API уже соответствует.** `getInvitePreview` уже возвращает `{ ok: false, code: "NOT_FOUND", message }`, а `toResponse` уже отдаёт 404 (`apps/web/src/lib/api-v1.ts:4-11`). Для `/i` меняется только HTML-страница (CLE-103) и тесты, фиксирующие неразличимость ответа и реальный 404. Собственная ссылка остаётся `FORBIDDEN` (403) — это не скрытая причина: владелец знает, что ссылка его.
4. **`/api/v1/me/gifts` — не публичное чтение.** Список создаётся при регистрации (AD-6), а его отсутствие у владельца — anomaly. `getMyGifts` уже отвечает `NOT_FOUND` после попытки починить строку (`apps/web/src/actions/my-gifts.ts:40-47`); это остаётся. Успешная схема `ListData` общая, поэтому `/me` тоже перестаёт отдавать `access: "not_found"` — на практике он его и не отдавал: anomaly уже была ошибкой.
5. **`/admin` — другой механизм, AC не меняется.** `Story 10.1` говорит «USER на `/admin` получает `not_found`»; это страница админки, а не публичный API, и в коде её ещё нет (`apps/web/src/app/admin` отсутствует). При реализации она получит тот же page-level 404 через `notFound()` и общий not-found UI; нормативного изменения не требует.
6. **`noindex`.** Сейчас явного `robots`-мета тега на `/l` и `/i` нет. Next автоматически вставляет `<meta name="robots" content="noindex">` в ответ со статусом 404, поэтому после перехода на `notFound()` индексация закрыта без ручной правки метаданных. Заголовки документа (`Список не найден — {brand}`, `Приглашение не найдено — {brand}`) остаются прежними.
7. **Ответ должен быть реально 404, а не 200 с текстом.** `notFound()` в `app/l/[token]/page.tsx` и `app/i/[token]/page.tsx` вызывается до старта стриминга (в этих сегментах нет `loading.tsx`/Suspense), поэтому Next успевает отдать статус 404. В кодовой подзадаче это проверяется HTTP-запросом, а не только компонентным тестом.
8. **Клиенты не показывают техническую диагностику.** `message` остаётся английской диагностикой (`Not found`), как требует AD-12/AD-27; экраны берут текст из каталога (`common.errors.code.NOT_FOUND`, `web.wishlist.notFound`, `web.invite.notFound`, `app.profile.notFound`) и не меняются.

## 4. Подход

**Прямая корректировка (Option 1).** Новое правило не требует ни новой таблицы, ни нового экрана: `VisibilityPolicy` уже умеет отличать «не видно» от найденного, `toResponse` уже отображает `NOT_FOUND` в 404, а `notFound()` в Next уже даёт реальный 404 и общий not-found UI. Меняются: успешная схема контракта (минус ветка `not_found`), три use-case/адаптера, мапперы мобильного клиента, две страницы и тесты.

**Почему не оставить `ok: true`.** Вариант без правки архитектуры — привести `/i` к gate-ответу `ok: true, access: "not_found"` — отклонён владельцем: он противоречит REST (404 — это ошибка, а не успешное чтение), заставляет каждый клиент проверять `ok` и `access` отдельно и оставляет HTML-страницы с 200 (CLE-103 не закрывается). Выбранный вариант — лучшая практика и уже поддерживается транспортом и `toResponse`.

**Почему не менять AD-21/AD-26.** Они описывают механику приглашения и монорепозиторий и не упоминают `not_found` или HTTP-статус; правило уже живёт в AD-7/AD-12. Точечная правка не нужна.

**Трудоёмкость:** низкая-средняя (0,5–1 день): схема контракта, три use-case, мапперы клиента, две страницы и общий not-found UI, тесты.

**Риски:**

| Риск | Закрытие |
|---|---|
| Разные причины «не найдено» станут различимы по статусу, телу или заголовкам | Все причины идут через один `toResponse({ ok: false, code: "NOT_FOUND", message: "Not found" })`; `Cache-Control: private, no-store` одинаков; тест сравнивает статус, тело и заголовки (кроме `Date`/`Content-Length`) для неизвестного, битого и Block |
| `notFound()` отдаст 200, если ответ уже начал стримиться | В сегментах `/l/[token]` и `/i/[token]` нет `loading.tsx`/Suspense; кодовая подзадача проверяет реальный статус HTTP-запросом, а не только рендером компонента |
| Страница и API разойдутся: API 404, страница 200 | Обе стороны используют один `readWishlist`/`getInvitePreview`; AC Story 3.3/4.7 фиксируют оба ответа; тесты страниц и роутов |
| Мобильный клиент покажет общую ошибку вместо «Список не найден» | Мапперы `public-wishlist.ts`, `profile.ts`, `invite-link.ts`, `my-gifts.ts` переводят `{ ok: false, code: "NOT_FOUND" }` в существующее состояние `access: "not_found"`; тексты и экраны не меняются, тесты экранов остаются |
| `access: "not_found"` останется в контракте и кто-то продолжит его отдавать | Ветка удалена из `listDataSchema`; все места компилируются/тестируются; `git grep` в отчёте перечисляет осознанные остатки (`domain/visibility`, внутренние состояния экранов) |
| `/me` сломается из-за общей схемы | Владельческое чтение и раньше не отдавало `not_found` при найденном списке; anomaly уже была `NOT_FOUND`. Маппер `my-gifts.ts` сохраняет экран «Список не найден» через `NOT_FOUND` |
| Утечка причины через текст `message` | `message` — одна английская строка «Not found» для всех причин; клиенты её не показывают (AD-27) |
| Кто-то прочитает AD-7 «Prevents: 404 как маскировка» буквально и вернёт 200 | AD-7 и AD-12 явно говорят: различимый ответ запрещён, единый 404 обязателен; в §5.1 это в первой строке AD-7 |
| Поисковик проиндексирует страницу «не найдено» | Next вставляет `noindex` в ответ 404 автоматически; это проверяется в кодовой подзадаче |
