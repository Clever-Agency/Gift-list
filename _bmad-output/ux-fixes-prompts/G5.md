## Bug (reproduced live with Playwright)
Open http://localhost:8081/gifts/new with a FULL page load (the previous history entry is another document), type a title, press browser Back -> our dialog «Сохранить изменения?» -> «Не сохранять». proceed() (lines ~120-130) calls window.history.go(-2) while the `beforeunload` listener (registered at ~98-106 while enabled) is still attached; the navigation crosses documents, so the browser shows its native "Leave site?" confirm on top of the user's explicit choice.
The same can happen on any other deliberate exit while the listener is attached: allowLeave() (save success, «Не сохранять» via the screen's «Отмена», session-expired hand-over), and proceed() via use-discard-guard when a navigator action is replayed.

## Expected
Once the app itself decides to leave (proceed(), allowLeave()), the beforeunload handler is removed (or becomes a no-op) BEFORE any history.go/back or router navigation happens, synchronously. revokeLeave() (failed exit, form still mounted and dirty) re-arms it. Cancel (cross/Esc) keeps it. Keep everything else in the hook unchanged.
Suggested: keep the handler in a ref and a `detachUnload()` helper; or make onBeforeUnload return early when `leaving.current` is true (and set leaving before go). Prefer real removal + idempotent cleanup.

## Constraints

## Acceptance criteria
1. After a blocked Back, proceed() => dispatching a real `beforeunload` Event (cancelable) is NOT defaultPrevented, and history.go was called after the handler was detached.
2. After allowLeave() => beforeunload not prevented.
3. After revokeLeave() while still enabled => beforeunload prevented again.
4. After cancel() => still prevented.
5. Existing tests pass.

## Tests to write

Spy on window.history.go only to check ORDER (handler already inert at the time go() is invoked: inside the spy dispatch beforeunload and assert not prevented).
